## Private catalogue and storage direction

Use the existing lowercase `data/` convention. The proposed future structure
has `data/catalog/` for durable private identities and state,
`data/raw/raas/<source-session>/<session-interval>/<job-id>/output.mcap`
for future staged downloads, and `data/derived/` for validated numeric archives.
Existing diagnostic/registration artifacts stay in versioned `outputs/` paths.
This is a planning convention, not a migration or a tested controller.
Keep the current registered file in place until a reviewed path amendment exists.

The private catalogue should retain source-session, interval and job IDs as
different entities; acquisition/export configuration, original filenames,
merged-input provenance, exact raw identity, retrieval locator/evidence,
versioned report/archive hashes and explicit processing/retirement state.
Repeated `output.mcap` basenames are safe only within distinct identity folders;
a later generic export needs a scoped key rather than the old pinned cohort's
basename-only assumptions. Directory count and job count are not outing count.
Jobs/intervals/reruns from one source session stay in the same conservative
group until evidence establishes distinct physical outings. Unknown stays unknown.

Keep durable catalogue records or explicit tombstones after an authorized raw
retirement; empty folders alone do not record what was processed or removed.
Catalogue/source metadata remain private and outside public Git. A download/
register/inventory/decode/readiness/export/validate/retire controller must model
each state separately, verify lineage and enforce storage budgets. Raw deletion
requires reviewed archive completeness and retrieval of the exact original bytes;
temporary scratch cleanup is a different operation.
